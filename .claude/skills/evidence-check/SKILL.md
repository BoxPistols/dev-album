## 前提: 判定を層で分ける

プロンプトで「正確に引用して」と頼むだけでは捏造・言い換えを検出できない。
**決定的に取れるものを判断に回さない**。この順で当てる。

| 層 | 何を見るか | 手段 | 誤検出 |
|---|---|---|---|
| L1 | 出典レジストリの書式 | `pnpm test src/data/sources.test.ts` | なし |
| L2 | 逐語引用が原文にあるか | `pnpm check:sources` | なし |
| L3 | 監査の判定に書いた引用が原文にあるか | `pnpm check:verdicts <判定JSON>` | なし |
| L4 | 実測の再現性 | `reproduce` コマンドを手で回す | なし |
| L5 | レジストリに載っていない主張 | ここで初めて読んで判断する | あり |

L1〜L4 が緑になるまで L5 をやらない。順序を逆にすると、機械で落とせるものを
人が読んで見逃す。

## 判定の引用は「装飾なしの逐語 1 本」で書く

`docs/audits/*-verdicts.json` の `quote` は、L3 が原文と文字列一致で照合する。
次を入れると、判定自体が正しくても照合に落ちる。

- 出典ラベルの前置き（`RFC 9112 Section 2.1: "..."`、`[https://...] "..."`）
- ページ名の付加（`【quick-start.html】「...」`）
- 引用符での囲み（原文自体に含まれる場合を除く）
- 複数箇所・複数ページの引用を `/` や改行で連結したもの
- 表のセルやコードブロックを詰めて 1 行にしたもの
- 自分の注記（`(略、同 README の別節)`）

2 箇所必要なときだけ中略記号 `[…]` で繋ぐ。原文の言語のまま貼る（訳さない）。

**この書式を指示しないと 4 分の 1 が照合できなくなる。** 実測で、書式を指示せずに
判定した 547 件は 74% しか一致せず、指示した 386 件は 99% 一致した。差は判定の質
ではなく引用の書き方だけだった。

一致しなかった引用は、出典を取り直して選び直す。その過程が判定の再検証になる
（169 件を書き直したとき、判定が変わったものが 2 件あった）。

## 引用は「動く出典」に固定しない

`sourceUrl` に、内容が時間とともに書き換わる URL を選ぶと、判定が正しくても照合が必ず
いつか落ちる。判定した日は緑で、数日後に赤くなる。

実測で落ちた例:

- `api.github.com/repos/<owner>/<repo>/releases/latest` — 新しいリリースが出た時点で外れる
- `api.npmjs.org/downloads/point/last-month/<pkg>` — 数値が毎日動く

同じ内容を指す固定版に差し替える。

- `releases/latest` → `releases/tags/v2.55.0.windows.5` のように版を打つ
- `last-month` → `point/2026-07-01:2026-07-31/<pkg>` のように期間を打つ
- 一覧ページの「最新」欄 → その版の固有ページ

差し替えたら `evidence` に「元は動く URL だった」と書き残す。次に同じ出典を触る人が
`latest` へ戻さないため。

数値そのものが主張の根拠になっている場合（ダウンロード数で「最も使われている」を支える等）は、
その数値が代理指標にすぎないことも `evidence` に書く。期間を固定しても、比較対象を
網羅したことにはならない。

## 手順

### 1. 機械で取れるものを取る

```bash
pnpm test src/data/sources.test.ts   # レジストリの書式
pnpm check:sources                   # 実際に URL を取得して逐語照合
```

`check:sources` が「引用が本文に見つからない」と言ったら、原因は 2 つに 1 つ。

- **原文が変わった**: 一次情報を読み直し、引用と本文の記述の両方を更新して `verifiedAt` を今日にする
- **引用が正確でなかった**: 本文の主張ごと見直す。引用を原文に合わせて直すだけで済むとは限らない

**引用を通すために正規化を緩めない。** `normalize()` が吸収してよいのは
バッククォート・Markdown リンク記法・`<code>` 境界の空白・引用符の字体まで。
語を落とす正規化を足すと、言い換えた引用が通るようになり仕組みが死ぬ。

### 2. 実測の主張を再現する

`kind: "measured"` の出典は `check:sources` が再現コマンドを一覧表示する。
バージョンを固定したまま実際に回し、`note` の記述と一致するか確かめる。

一致しなくなっていたら、それは**上流が直った**ということ。教材から落とすか、
「どの版で再現し、どの版で直ったか」を書く。黙って残さない。

### 3. レジストリに載っていない主張を洗い出す

対象ページを読み、事実を主張している文を拾う。次に当たるものは要注意。

- ツールの挙動（「〜が自動的に読む」「〜すると再読込される」）
- 数値（行数・件数・比率・バージョン）
- 「公式が推奨している」「標準化が進んでいる」
- 全称・存在の否定（「〜するツールはない」「必ず〜になる」）

拾った文ごとに次を判定する。

- 一次情報がある → レジストリに逐語引用つきで足す
- 自分で再現できる → 実際に回して `kind: "measured"` で足す
- 他者の測定に依る → `kind: "secondary"` にし、**本文にも引用であることを書く**
- どれでもない → **書かない**。断定を弱めるのではなく、その文を落とす

### 4. 「分からない」を残す

一次情報に当たっても確定しなかった項目は、確定しなかったと書く。
`「公式に該当記載なし」` は正当な結論であって、埋めるべき欠落ではない。

推測で埋めた一文は、読者からは確認済みの記述と見分けがつかない。
「分からない」と書かれた読者は別の手段を探すが、断定された読者は何もしない。

## 再監査の手順

監査をやり直して `docs/audits/*-verdicts.json` と `sources.generated.ts` を作り直すときは、
この順で通す。順序を変えると、引用の書き方の問題と原文の変化が混ざって見えなくなる。

```bash
pnpm check:verdicts <判定JSON>   # 1. 判定の引用が原文にあるか（L3）
#   → 判定から sources.generated.ts を生成する
pnpm fix:quotes                  # 2. 引用を「原文に連続して現れる部分」まで切り詰める
pnpm check:sources               # 3. レジストリ全体を逐語照合する（L2）
```

`fix:quotes` は `scripts/trim-quotes.mjs --write`。生成元のエージェントが原文で離れた文を
つないで 1 つの引用にしていることがあり、そのままでは `check:sources` が正しく落ちる。
通すために正規化を緩めるのではなく、確認できた範囲まで引用を短くし、確認できなければ捨てる。

`pnpm check:quotes` は同じことを書き換えずに行い、変更が出るなら exit 1 を返す。
生成直後の確認と、時間が経ってから「引用がまだ原文にあるか」を見るのに使う。
取得不可の出典は `fix:quotes` で登録から外れるので、一時的な障害でないかを個別に
再実行して確かめてから反映する。

## リダイレクトを恒久 URL へ寄せる

`pnpm check:links` は「切れている」だけでなく「リダイレクトされる」も数える。
リダイレクトは今は届くが、出典側が次に整理したときに切れる。届くうちに寄せておく。

```bash
pnpm check:links --json > /tmp/links.json   # 確認結果を機械可読で出す
pnpm fix:links /tmp/links.json              # 何をどう書き換えるかを出すだけ
pnpm fix:links /tmp/links.json --write      # 実際に書き換える
pnpm check:links                            # 書き換えた URL が本当に届くか測る
```

**最後の再実行を省かない。** 書き換えは 2 種類の壊し方をする。どちらも実測しないと見えない。

1 つ目は、短い URL が長い URL の内側に入っているとき。`/docs/installation` が
`/docs/installation/using-vite` へ飛ぶ場合、同じファイルにある後者の前半が置き換わって
`/docs/installation/using-vite/installation/using-vite` ができる。境界を見て、
URL の直後に続きがあるなら触らない（`fix:links` は対応済み）。

2 つ目は、ロケール接頭辞を落とせると思い込むこと。この検査は `accept-language: en` を
送るので `docs.github.com/actions` は `/en/actions` へ飛ぶ。そのまま書くと日本語で読む人にも
英語版を強制するので落としたいが、readthedocs の `/en/stable/` は実際のパスで落とすと 404 になる。
静的には見分けが付かないので、落とした URL が届くかを取得して確かめてから採る（同上）。

`fix:links` が書き換えないもの: 末尾スラッシュ・スキーム・クエリだけの差、
ログイン画面や検索結果や別ホストのトップへ飛ばされるもの。

## 修正した後にやること（修正 pass の独立レビュー）

修正 pass のあとに、**修正内容だけを対象にした独立レビュー**を工程として入れる。
修正作業そのものが新しい誤りを持ち込むからで、これは仮定ではなく実測。
166 件の事実誤りを直した作業で、後から入れた全体レビューが修正由来の誤りを 5 件拾った。

- 出典に書いていない定義を、その出典に帰属させた
- 例外条件の数値を代表値として採用し、通常経路の値が消えた
- 本文は正しいのに、図のラベルだけ出典に無い区分を作った
- 裏づけの無い記述を落とす作業の中で、裏づけの無い記述を足した
- リポジトリから確認できない値を断定した

加えて、誤った判定（REFUTED）を根拠に本文を書き換えたケースも 1 件あった。
修正エージェントには「判定を鵜呑みにせず出典を自分で確かめる」と指示していたが、
確かめた結果を誰も検算していなかった。

レビューの観点は次の 6 つ。

1. 削除で意味が壊れた文が無いか（主語の消失、箇条書きの項目数と本文のズレ）
2. 断定を薄めただけの記述が残っていないか（帰属つきは正当なので区別する）
3. 同じ主張がページ内・別ページで食い違っていないか（Quiz の explanation、図、CodingChallenge の hints）
4. 新しく書いた記述が、それ自体で新しい誤りになっていないか（数値・単位・バージョン・コマンド名を自分で取得して確かめる）
5. 規約違反が無いか（色トークン直書き、変動数値、情緒的コピー）
6. 変動しやすい値に基準日が付いているか

**レビュー担当は修正しない。** 指摘だけを出し、直すのは修正担当に戻す。
レビュー側が直すと「指摘」と「対応」が混ざって、何が確認されたのかを追えなくなる。
判定が誤っている可能性も、このレビューで初めて想定に入れる。

## 禁止

- 要約・翻訳を `quotes` に入れる（訳す場合は本文側で「訳は筆者」と明記して原文を併記）
- 相手が言っていない言い回しを引用符の中に入れる
- 二次情報を一次情報として提示する
- `verifiedAt` を実際に照合せずに更新する
- 検証が落ちたときに、検証のほうを緩めて通す

## 落とし穴

- **0 件で成功するチェックを信用しない。** レジストリの解析に失敗して空配列を返せば
  「照合 0 件・失敗 0 件」で緑になる。`verify-sources.mjs` は 0 件を事故として投げる
- **新しい検査は一度壊して赤を見る。** 偽の引用を仕込んで落ちることを確認してから信用する
  （捏造・言い換え・語の脱落・数値改変・離れた 2 文の無断連結の 5 種で試すとよい）
- **`cmd | tail` の終了コードは `tail` のもの。** 成否は出力の中身で確認する
- **不一致が大量に出たら、まず検査側を疑う。** 実測で、不一致 207 件のうち大半は
  引用の誤りではなく取得・正規化の取りこぼしだった。数を人に出す前に、
  実際に何件かを原文と突き合わせる
- **一致しないものを黙って「一致」にも「不一致」にも混ぜない。** 平文化できない
  （PDF で `pdftotext` が無い等）ものは未照合として別に数える。道具の不在と
  引用の誤りは別の問題で、混ぜると片方が見えなくなる
- **取得側の癖で偽の不一致が出る。** 実際に踏んだもの:
  - GitHub の blob ページは本文が JS 埋め込みなので raw を引く
  - ブラウザを騙る UA を弾く出典がある（w3.org は素直な UA なら 200）
  - meta refresh は fetch が追わない（nuxt.com は本文が 125 字で終わる）
  - 言語を指定しないと別言語版が返る（web.dev がポーランド語版を返した）
  - Wayback は連続アクセスで 503 を返す。再試行すると通る
  - クライアント描画のサイトは HTTP 応答に本文が入らない（m3.material.io は
    「This website requires JavaScript.」だけを返す）。`source-fetch.mjs` の
    `BROWSER_RENDERED_HOSTS` に足すと chromium で描画してから照合する。
    許可リストに載らない URL はブラウザを通らないので、通常実行は遅くならない。
    chromium が入っていない環境では「未照合」になる（不一致には混ざらない）
- **まとめて回した結果の失敗は、個別に再実行して確かめる。** 一時的な取得失敗が
  混ざる。1 件だけ落ちたときは特に疑う
