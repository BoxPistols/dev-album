新規ページの土台は `create-page` が作る。このスキルは**中身の作り方**を扱う。
出典の検証手順そのものは `evidence-check` にある。

## 原則

### 推測と実測を書き分ける

読み手は「〜のはず」と書いてあっても、こちらの実測結果として受け取る。
だから文ごとに根拠の強さが分かる書き方にする。

| 根拠 | 書き方 |
|---|---|
| 一次情報 | 「公式ドキュメントは〜と明記している」＋逐語引用 |
| 手元の実測 | 「〜で試すと〜になる」＋バージョンと再現コマンド |
| 他者の測定 | 「〜が公開している測定によれば」＋リンク |
| 確定しなかった | 「公式に該当記載なし」と書く。埋めない |

### 仕様値と実測値のギャップを先に出す

「仕様で定義された値」と「実環境で観測される値」がズレる箇所は先に明示する。
学習者が「定数＝神聖」と思い込むと、実測がずれたときに自分を責めて折れる。

書き方のテンプレは **「仕様では X、実測では Y になることがある。理由は Z」** の 1 段落。
理論的な導出は本文に混ぜず、末尾にまとめて本文を簡潔に保つ。

### 引用の忠実性

- 訳を原文の引用として出さない。訳すなら「訳は筆者」と書くか原文を併記する
- 読みやすく言い換えた時点で引用ではない。「以下は要約」と書く
- 相手が言っていない言い回しを引用符の中に入れない。数値だけ報告されたものに
  自分の表現を足すと捏造になる

事実が正しくても、引用の扱いが雑だと資料全体の信頼が落ちる。

### 打ち消しが要る文は書き方が誤っている

「A は B です。ただし C という意味ではありません」と打ち消しを足したくなったら、
A が 2 通りに読めている。打ち消しでは直らないので A を書き直す。

## 手順

1. **対象の一次情報を特定する。** ベンダー公式ドキュメント、仕様リポジトリ、
   公式アナウンス。二次情報から書き始めない
2. **一次情報を読む。** 検索結果の要約で済ませない。仕様は実装と食い違うので、
   可能なら実装（リポジトリのソース）も見る
3. **再現できるものは自分で回す。** バージョンを固定し、出力をそのまま控える。
   伝聞を実測に格上げできる箇所は必ず格上げする
4. **`client/src/data/sources.ts` に出典を登録する。** 逐語引用・`verifiedAt`・
   `usedBy`（ページの path）を埋める。実測は `reproduce` を必ず書く
5. **本文を書く。** `ReferenceLinks` で出典を冒頭か末尾に出す。
   ページ内の主張と登録した出典が対応していることを確認する
6. **検証する。**
   ```bash
   pnpm test src/data/sources.test.ts
   pnpm check:sources
   pnpm check && pnpm test && pnpm build
   ```
7. **実ブラウザで見る。** ビルドが通ることと意図どおり描画されることは別。
   狭い画面・長い文言・新規追加した状態は特に見落としやすい
8. **`announcements.ts` の先頭にエントリを足す**（`CLAUDE.md` の教材更新ルール）

## 書かないもの

- 出典のない「主流化している」「標準になりつつある」
- 全称の否定（「〜するツールは存在しない」）。確認できた範囲に言い換える
- 変動する具体値（ページ数・ステップ数）。`navigation.test.ts` が正本
- エモーショナルなコピー、ネガティブ訴求、クリシェ

## 名前の衝突を確認する

新しい概念名・ファイル名を教材で使う前に、その名前が既に別の意味で使われていないか
検索する。同名の実在仕様があると、読者が調べた瞬間に別物に行き着く。

実例: 第 3 のメタドキュメントを `DESIGN.md` と呼んでいたが、`DESIGN.md` は
Google Labs が公開したデザイントークン記述フォーマットの名前として実在した。
`ARCHITECTURE.md` に改名し、同名の別仕様を扱うページを別に立てて解決した。
