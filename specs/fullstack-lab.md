# specs/fullstack-lab.md（草案）

## 概要
フルスタックコース（[fullstack-course.md](./fullstack-course.md)）の演習を、ブラウザだけで完結するオンラインの開発環境（以下「ラボ」）で行う。ラボはDev Albumとは別のアプリとして作り、Dev Albumの教材ページから課題単位で開く。

いまのDev Albumの演習は穴埋めが中心で、正誤はキーワードの一致で見ている。ラボでは受講者が自分で考えたコードや、AIと壁打ちして書いたコードを提出し、次の2段で見る。

1. 機械で決められること（テストが通るか、型が合うか、lintに引っかかるか）は機械で判定する
2. 機械で決められないこと（設計の妥当さ、読みやすさ、なぜそう書いたかを説明できるか）はAIがレビューし、プログラミング教室の講師のように助言と次の一歩を返す

ローカルに開発環境は作らない。エディタ・ターミナル・プレビューがブラウザの中にある、VS Codeをブラウザで開いたような画面にする。

## 入力

### 課題の種類

| 種類 | 受講者が出すもの | 判定 |
|---|---|---|
| 実装課題 | 自由に書いたコード（AIと書いたものも可） | テスト・型・lintで合否、AIが設計と読みやすさをレビュー |
| 設計課題 | ER図（Mermaid）、APIの設計、ADRなどの文章 | AIがルーブリックに沿ってレビュー（合否は出さず、達成度と助言） |
| 説明課題 | 自分のコードについての説明（なぜそう書いたか、他の案と比べて何を選んだか） | AIが説明とコードの食い違いを指摘し、理解を確かめる質問を返す |
| 穴埋め | 既存と同じ | 既存と同じ（ラボでは扱わなくてよい） |

AIと壁打ちして書いたコードを出すことは禁止しない。代わりに説明課題を実装課題とセットにし、「自分の言葉で説明できるか」で理解を確かめる。

### 課題の定義（1課題 = 1ディレクトリ）

```
exercises/fullstack/<step-id>/
├── meta.json          # 課題の種類（implementation / design）、工程、最初に開くファイル
├── learn.md           # 基礎（この課題を解くのに要る考え方。図つき）
├── quiz.json          # 基礎の理解を確かめる小テスト（3〜4問、解説つき）
├── exercise.md        # 課題文（目的・ユーザーストーリー・受け入れ条件・詳細仕様）
├── starter/           # 開始時のファイル一式（前の課題の模範解答から作る）
├── tests/             # 受け入れテスト（Vitest）。受講者にも見える
├── rubric.json        # AIレビューの観点（観点ID、説明、達成の目安）
└── solution/          # 模範解答（受講者が「見る」を押したときだけ出す）
```

`exercise.md`は、どの課題も次の4つの見出しを持つ（単体テストで確かめる）。実装の前に「何のために、誰の、どんな困りごとを解くのか」を読んでから手を動かすため。

| 見出し | 書くこと |
|---|---|
| 目的 | この課題で作るものが、プロダクトの中で何の役に立つか |
| ユーザーストーリー | 「〈利用者〉として、〈したいこと〉をしたい。なぜなら〈理由〉」の形で1〜3本 |
| 受け入れ条件 | `tests/`が確かめること。ストーリーごとに |
| 詳細仕様 | 型・制約・名前など、実装で迷う点の決めごと |

コースの最初の課題は設計課題「要件定義を書く」にする。受講者が`docs/requirements.md`に目的・利用者・ユーザーストーリー・受け入れ条件・スコープ外・未決事項を書き、テストは形式（見出しがそろっているか、ストーリーが決まった形か、ストーリーごとに受け入れ条件があるか）だけを見る。中身はAIがルーブリックでレビューし、合否は出さずに達成度と助言を返す。後の実装課題の課題文は、この要件定義の模範解答と食い違わないように書く。

`rubric.json`の観点は課題ごとに3〜5個に絞る。CodingChallengeのヒント設計（1 keyword = 1 hint）と同じで、観点が多すぎるのは課題が大きすぎる合図として分割する。

## 処理フロー

### 入口（コースの地図）
- 課題を開発の工程（要件定義 → 設計 → 実装 → テスト → リリース）の順に並べる。工程ごとに、何をする段階かの一文と、その工程の課題を置く
- まだ作っていない課題も「準備中」として並べ、コース全体の道のりが最初から見えるようにする
- 課題ごとに進み具合（学んだ / 読んだ / 提出した / 合格した・形式がそろった）を出す。進み具合はIndexedDBにだけ置く

### 課題の4段
課題を開くと、いきなりエディタではなく、次の4段で進む。上部に段の表示を置き、どの段にも戻れる。URLに段を持たせる（`?exercise=…&step=learn`）。

| 段 | 画面 | 中身 |
|---|---|---|
| 1. 基礎を学ぶ | 読みやすい幅の1カラム | `learn.md`（考え方と図）と小テスト。小テストは答えるとその場で正誤と解説が出る。全問に答えると「学んだ」になる（正解しなくても進める。間違えた問は解説を読んでから進む前提） |
| 2. 課題を読む | 同上 | `exercise.md`（目的・ユーザーストーリー・受け入れ条件・詳細仕様）。最後に「この課題で手を動かすファイル」と「確かめられること」をまとめて出す |
| 3. 取り組む | エディタ（下の「画面」） | ここで初めてエディタ・ターミナル・プレビューを出す。WebContainerの起動とインストールは1段目を開いた時点で裏で始め、3段目に来るまでに済ませておく |
| 4. 振り返る | 1カラム | 最後に提出した結果（機械判定とAIのレビュー）、模範解答との差分を開く入口、次の課題への案内。まだ提出していなければ3段目へ戻る案内 |

### 画面（3段目）
1. VS Codeと同じ配置にする。左端のアクティビティバー（ファイル / 課題 / 提出とレビュー / 模範解答）で左のサイドバーの中身を切り替え、中央はエディタ（Monaco。開いているファイルのタブ付き）とプレビューを左右に並べ、下にターミナル（xterm.js）を置く。区切りはドラッグで幅を変えられる
   - プレビューは常に見える位置に置く。準備中は「起動 → インストール → サーバー起動」の進み具合と経過時間を出し、準備ができたら自動で表示する。別のタブで大きく開くボタンを付ける
   - 設計課題（Markdownを書く課題）では、プレビューに書いている文書の表示を出す
   - 模範解答は、受講者が「模範解答と比べる」を押したときだけ、エディタの場所に差分表示（Monacoの差分エディタ。左が自分のコード、右が模範解答、構文の色分けつき）で出す
   - 選択中のタブや項目は、片側だけの色付き線ではなく背景の塗りで示す
2. 受講者のコードはWebContainer（ブラウザの中で動くNode.js）で動かす。`npm install`・開発サーバー・テストはすべてブラウザ内で走り、受講者ごとのサーバーは要らない
3. ファイルはブラウザのIndexedDBに保存し、タブを閉じても続きから再開できる。zipで書き出せる

### 提出とレビュー
1. 受講者が「提出」を押す
2. 機械判定: WebContainerの中で`tsc --noEmit`・`eslint`・`vitest run --reporter=json`を走らせ、結果をJSONで集める
3. AIレビュー: 課題文・`rubric.json`・受講者のコード（starterからの差分）・機械判定の結果・説明課題の文章をサーバー側のAPIに送る
4. サーバーはAIに、決めたJSONスキーマで返させる。Zodで検証し（`advice`は`z.array(z.string()).max(3)`、`questions`も同じく上限を付ける）、形が合わない応答は捨てて1回だけ再試行する

```ts
type Review = {
  rubric: {
    id: string;
    level: "met" | "partial" | "not_met";
    // levelを誰が出したか。heldはJevの確信度が0.8未満で判定を保留したもの（levelはLLMの判定を参考として残す）
    levelSource: "jev" | "llm" | "held";
    confidence: number | null;   // Jevの確信度。LLMの判定ならnull
    evidence: { file: string; line: number }[];
    comment: string;
  }[];
  advice: string[];          // 次に直すとよい点（多くても3つ）
  nextHint: string | null;   // 答えそのものではなく、次の一歩
  questions: string[];       // 理解を確かめる質問（説明課題）
};
```

5. 画面には機械判定の結果を先に、AIレビューをその下に出す。合否は機械判定だけで決め、AIは合否を変えない
6. 受講者はAIの指摘ごとに「納得した / 違うと思う」を返せる。「違うと思う」は理由と一緒に記録し、ルーブリックとプロンプトの見直しに使う

### AIレビューの方針
- 答えを書かない。「ここを直すとよい」は指摘するが、直したコードは出さない。模範解答は受講者が明示的に開いたときだけ見せる
- 根拠の行を必ず付ける（`evidence`）。行を示せない指摘は出さない
- 観点ごとの判定（met / partial / not_met）は分類の問題なので、Jev（TypeSafe AI）の中継サーバーに寄せられるかを第0段階で試す。寄せられれば、自由文の助言だけをLLMに書かせる
- 利用枠と自分のAPIキー（BYOK）はDev Albumの`/api/chat`と同じ仕組みにする（`api/lib/chatLimits.ts`の上限と匿名の1日枠）

### ラボの中で動かすスタック
WebContainerで動くものに限る。第0段階の調査で次がわかっている。

- Next.jsは15.4より新しい版がWebContainerで動かない。15.5以降が`AsyncLocalStorage`に依存し、WebContainerが未実装のため。16の`next dev --webpack`も実行時エラーになる報告がある（stackblitz/starters#122）
- TurbopackはネイティブバイナリでWebContainerでは使えない。WASM版は`next dev`に必要なAPIが欠けている

そこでラボの中は次の構成にする（決定事項を参照）。

| 層 | ラボの中 | 本番（shipセクション） |
|---|---|---|
| フロント | Vite + React + TypeScript + Tailwind | Next.js（App Router）に載せ替える手順を教材で示す |
| API | Hono（Node.js） | 同じHonoをCloud Run / Vercel Functionsに配備 |
| DB | PGlite（WASM版のPostgres）+ Drizzle | Supabase / NeonのPostgres |
| 認証 | 課題用の簡易セッション。RLSは`set_config('app.user_id', …)`と`current_setting`で組む | Supabase Auth（`auth.uid()`に置き換えるだけで同じポリシーが効く） |
| 非同期 | `FOR UPDATE SKIP LOCKED`のジョブテーブルを自分で書く（第0段階で、pg-bossもPGliteで動くことを確かめた。教材では先に手書きで仕組みを見せ、pg-bossへの差し替えはjobsセクションで扱う） | pg-boss + ワーカー |
| テスト | Vitest | Vitest + Playwright（GitHub Actions） |

RLSを`auth.uid()`ではなく`current_setting`で組むのは、Supabaseを外しても動くことと、`auth.uid()`の中身が同じ仕組みであることを先に見せられるため。

## エッジケース
- ブラウザがWebContainerに対応していない（Firefoxはプレビューに制限、Safariはベータ） → 入口で`crossOriginIsolated`を確かめ、使えないときは「Chrome / Edgeで開く」案内と、教材ページの読み物だけで進める道を出す
- サイトの配信ヘッダー → WebContainerはクロスオリジン分離（`SharedArrayBuffer`）が要る。ラボのホスティングでCOOP / COEPのヘッダーを付ける。Dev Album本体には付けない（外部の埋め込みが壊れるため。別アプリにする理由の1つ）
- テストは受講者から見える → 採点の不正防止はしない。目的は学習で、テストを読んで仕様を知ることも学習の一部とする
- AIが間違える → 合否は機械判定だけで決める。AIの指摘は「参考」と明記し、「違うと思う」で反論できる
- 受講者のコードにAIへの指示が書かれている（プロンプトインジェクション） → 受講者のコードはデータとして区切って渡す。合否はAIが決めないので、影響は助言の質に留まる
- AIの費用 → 1回のレビューで送る量をサーバー側で制限する（差分だけ、ファイル数と文字数の上限）。匿名は1日の回数に上限、BYOKなら上限なし
- 受講者のコードと進捗 → IndexedDBにだけ保存する。サーバーに送るのは、提出時のレビュー用データと、受講者が押した「納得した / 違うと思う」の記録だけにする。レビュー用データは保存しない。「違うと思う」の記録は、課題・観点・理由・指摘の本文だけを、ルーブリックとプロンプトの見直しのために直近5,000件まで保存する（決定事項7）。どちらもプライバシーページに書く
- WebContainer APIのライセンス → 公式は「営利目的の商用環境での本番利用」にライセンスが要るとし、プロトタイプやPoCには不要としている。公開前に、無料の学習サイトとして使う場合の扱いをStackBlitzに確認する（下の「公開前に解決が要る点」1）

## 出力
- 正常系: Dev Albumの`fullstack`の各ページから「ラボで開く」を押すと、その課題のstarterが入った状態でラボが開く。提出すると機械判定とAIレビューが出る
- 異常系: ラボが開けない（ブラウザ非対応・ライセンス・障害） → 教材ページの読み物と模範解答のリポジトリで進められる

## 第0段階の結果（2026-11-08）

Node.js 22で確かめたものと、WebContainerの中で確かめたものを分けて書く。

| 項目 | 結果 | 確かめた環境 |
|---|---|---|
| Vite + Hono + PGlite + Drizzle + Vitest | 動く。Viteの開発サーバーの`/api`をHonoに渡し（`@hono/node-server`の`getRequestListener`）、1つのサーバーでフロントとAPIを動かせる。スキーマは`drizzle-kit/api`の`pushSchema`でPGliteにそのまま作れる | Node.js 22。WebContainerの中は下の注記 |
| PGliteのRLS（`set_config` / `current_setting`） | 効く。`set role`で権限の無いロールに切り替えると、他人の行が見えず、他人の`user_id`での`insert`は`new row violates row-level security policy`で止まる。`set_config(..., true)`でトランザクションの中だけに限ることもできる | Node.js 22（PGlite 0.5.15） |
| `FOR UPDATE SKIP LOCKED` | 動く | Node.js 22（PGlite 0.5.15） |
| pg-boss | 動く（pg-boss 12.38.1）。ただしPGliteを`db`オプションに渡す薄いアダプタが要り、複数の文をまとめて送るクエリでは各文の結果を配列で返す必要がある（返さないと`a custom db must return the rows of every statement`）。`supervise`と`schedule`は切る | Node.js 22 |
| COOP / COEPの下でのMonaco・xterm.js | 動く。MonacoはCDNから読むと`require-corp`で止まるので、`monaco-editor`を同梱してワーカーをViteで組み込む | ラボのビルドをPlaywrightのChromiumで開いた |
| Jevで観点ごとの判定 | 返せる。ルーブリックの3段階（met / partial / not_met）をそのまま`choice`の選択肢にすると、観点ごとに確信度付きで返る。確信度0.8未満は「判定を保留」にし、自由文の助言と根拠の行はLLMに書かせる | Jevの`/v1/systemone` |

途中でわかったこと。

- TypeScriptの`latest`は7系（Goで書き直したネイティブ版）になっており、WebContainerでは動かない。課題のstarterは6系（6.0.3）に固定する。typescript-eslintも`<6.1.0`を要求する
- 課題のテストは受講者にも見えるが、提出時は課題の正本で上書きしてから走らせる。受講者がテストを書き換えても判定は変わらない
- WebContainerの中での通し（インストール → 開発サーバー → 提出 → 機械判定）は、ラボのE2E（`e2e/lab-flow.spec.ts`）で確かめる

## 決定事項
1. 演習はDev Albumとは別のアプリ（ラボ）で行う（2026-11-07決定）
2. エディタはWebContainer方式にする（2026-11-07決定）。GitHub Codespacesは受講者ごとにGitHubアカウントと利用枠が要るため採らない
3. 合否は機械判定（テスト・型・lint）だけで決め、AIは設計・読みやすさ・説明への助言を返す（2026-11-07、推奨案）
4. ラボの中のスタックはVite + React + Hono + PGliteにする（2026-11-07、推奨案で確定。実装前なら変更できる）。Next.js 15.5以降がWebContainerで動かないため。Next.jsの載せ替えはshipセクションで手順として教える。ラボだけNext.js 15.4に固定する案は、古い版を教えることになるので採らない
5. ラボのリポジトリ名は`dev-album-lab`にする（2026-11-07、推奨案で確定）。URLは公開時に決める
6. 観点ごとの判定（met / partial / not_met）はJevに出させ、確信度0.8未満は保留にする。Jevが使えないときはLLMの判定を使う。助言・根拠の行・質問はLLMが書く（2026-11-08、第0段階の結果から）
7. 「違うと思う」の記録は、受講者の端末（IndexedDB）とサーバー（Upstash Redisのリスト。直近5,000件）の両方に残す。サーバー側には課題・観点・理由・指摘の本文だけを置き、利用者を識別する情報は付けない（2026-11-08）
8. 課題文は目的・ユーザーストーリー・受け入れ条件・詳細仕様の4つの見出しを持ち、コースの最初は受講者が要件定義を書く設計課題にする（2026-11-09決定）
9. 画面はVS Codeと同じ配置にし、プレビューを常に見える位置に置く（2026-11-09決定）
