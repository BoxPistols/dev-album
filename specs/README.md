# specs/ — 機能仕様書（スペック駆動開発）

複数ページにまたがる機能・教材セクションの追加は、**まずここに仕様を書いてから実装する**。
仕様がコードの上位（正本）であり、実装は仕様の派生物とする。共通規約は [../AGENTS.md](../AGENTS.md)、
設計は [../DESIGN.md](../DESIGN.md) を参照。

## いつ使うか

**適用**: 複数ページ/ファイルにまたがる、API/データ設計を伴う、長期メンテする基幹、AI に反復実装を頼む機能。

**過剰（不要）**: CSS の微調整、原因特定済みのバグ修正、既存パターンの単純な踏襲、5 分以内で終わる変更。

## ファイル命名

- 仕様定義: `specs/<feature>.md`
- 技術設計（任意）: `specs/<feature>-design.md`
- 実装計画（任意）: `specs/<feature>-plan.md`
- 参考例: `specs/examples/`

## ワークフロー（6 フェーズ）

1. **仕様定義** `specs/<feature>.md` — 概要 / 入力 / 処理フロー / エッジケース / 出力を書く（Plan Mode で下書き→レビューで精緻化）
2. **技術設計**（任意） — 変更ファイル・データ構造・依存を書く
3. **実装計画**（任意） — 実装順・ブロッキング依存・各ステップの期待出力
4. **実装** — 仕様に基づいてコードを書く
5. **検証** — 仕様のエッジケースを最低 1 件テストに落とし、緑にする
6. **フィードバック** — 実装中に判明した仕様の不備を仕様書に反映する

**整合性の定期検証**: 実装と仕様は乖離する。折を見て「仕様書と実装の整合性を確認して」を回し、乖離があればどちらかを直す。

## テンプレート

```markdown
# specs/<feature>.md

## 概要
[目的・背景・影響範囲を 1〜3 文で]

## 入力
- param: type（必須/任意、制約）

## 処理フロー
1. ステップ1（必要なら使用ライブラリ/手法を明示）
2. ステップ2

## エッジケース
- ケース → 期待される結果/扱い

## 出力
- 正常系: [形・状態]
- 異常系: [扱い]

## 完了条件（検証可能な形で）
- [ ] 型チェック / 単体テスト / a11y が緑
- [ ] [機能固有の受け入れ条件]
```

実例は [examples/manual-section.md](./examples/manual-section.md)（教材セクション追加の実際の仕様）を参照。
